# Audit — Runtime perpétuel

**Couverture : 9 fichiers lus (`kernel.mjs`, `GATES.md`, `PRD_DARK_FACTORY_RUNTIME_AMBIANT.md`, `aquaman-intake.md`, `aquaman-gate.md`, les trois schémas JSON, `bridge/bridge.mjs`), 24 commandes exécutées** (autotest, journal, simulations réelles, watcher lancé/tué à répétition, crash simulé, écriture concurrente, sondes wmic/taskkill).

Toute commande a été exécutée soit sur le kernel réel (aucun contrat déposé dans le vrai `03_Master_Agreements/`), soit sur une **copie** de `kernel.mjs` dans `%TEMP%\audit_kernel_copy\kernel_test.mjs`, avec une seule ligne changée : `PORTAIL` devient paramétrable par variable d'environnement (`AUDIT_PORTAIL`), pour pouvoir simuler des scénarios de panne sans toucher au dépôt. **Aucun fichier source du dépôt n'a été édité par cet audit.** Une seule empreinte inévitable existe : exécuter `node kernel.mjs --autotest` sur le kernel réel, comme demandé par ce brief, a ajouté 15 lignes au vrai `_runtime/.etat/journal.jsonl` — effet de bord du kernel lui-même (défaut #8 ci-dessous), pas une édition manuelle.

## Verdict global

Le kernel est réel et ses trois portes déterministes tiennent — mais le mode `--watch` n'est pas un runtime perpétuel : c'est un `setInterval` sans superviseur, sans verrou anti-doublon et sans rejeu, si bien qu'une seule exception non rattrapée ou un simple redémarrage transforme une dormance déclarée en perte silencieuse et permanente d'événements, sans qu'aucune ligne du journal ne le signale.

## Dormance ou mort — le test du réveil

- **Le portail `03_Master_Agreements/`** : le seul réveil possible est un dépôt de fichier humain (Summers, B1). Si personne ne dépose rien, rien ne se passe — et surtout, **rien ne le mesure**. Ce n'est pas la dormance décrite par le PRD (« état documenté, conditionnel, réversible, armé de déclencheurs ») : le déclencheur existe (le dossier surveillé), mais aucune horloge ne compte les cycles à vide pour distinguer « 3 semaines normales » de « 3 semaines oubliées ». Le README du portail (`00_Summers_CEO/03_Master_Agreements/README.md`) documente honnêtement l'intention, mais documenter une intention n'est pas l'instrumenter.
- **Le watcher lui-même** : qui le réveille s'il meurt ? Réponse mesurée : **personne, rien**. Pas de supervision de processus (pas de `pm2`, pas de service Windows, pas de cron de vérification), pas de heartbeat écrit dans le journal, pas de fichier PID. Le défaut #2 montre qu'une seule exception suffit à l'arrêter, et le défaut #1 montre qu'un simple redémarrage manuel ne rattrape pas ce qui s'est passé pendant l'arrêt. Un `--watch` mort ressemble, du point de vue du journal, à un domaine parfaitement dormant : silence dans les deux cas. **Le kernel ne distingue pas ces deux silences**, ce qui est exactement l'inertie déguisée en dormance que la mission demandait de traquer.
- **Un contrat orphelin (défaut #3)** : personne ne le réveille. Il n'existe même pas de requête possible (`--journal` liste tout, mais rien ne signale « cet événement n'a pas de suite causale »).

## Ce qui tient

- **Les trois portes déterministes fonctionnent réellement**, pas seulement sur le papier : `node kernel.mjs --autotest` → `12 reussites, 0 echecs` reproduit à l'identique le résultat déclaré dans `GATES.md:17`.
- **La frontière typée rejette vraiment le malformé** : testé directement (champ inconnu, statut hors enum, motif trop court) → tous rejetés et journalisés en `kernel.event.rejected`, jamais silencieusement ignorés.
- **Le déclencheur canonique est vraiment le seul** : `node kernel.mjs --simule "$TEMP/hors-portail.md"` → `REJET declencheur : ['chemin ne respecte pas le motif 03_Master_Agreements']`. Impossible de contourner le portail via `--simule`.
- **`shadow: true` est honnête** : les trois verdicts obtenus (réels et simulés) portent tous `(shadow)`, conformément à `GATES.md:58` — aucun agent ne peut lui-même passer `shadow: false`.
- **L'écriture concurrente n'a pas corrompu le journal à petite échelle** : 8 processus `--simule` lancés en parallèle sur le même `journal.jsonl` → 24 lignes, 0 ligne JSON corrompue (vérifié par parsing systématique). Ce n'est pas une preuve d'atomicité garantie à plus grande échelle (voir Questions ouvertes), mais à ce volume, ça tient.
- **`GATES.md` est honnête sur ses propres limites** : G8 et les trois manques listés en fin de fichier (extraction lexicale, un seul domaine, aucun connecteur sortant) sont déclarés non résolus plutôt que maquillés.
- **Le PRD lui-même nomme le piège de la préservation passive** (§7.3) et refuse explicitement de bloquer le MVP sur des travaux parallélisables — la doctrine anti-inertie existe et est appliquée à la marge du document, même si le code ne l'instrumente pas encore (défaut #6).

## Questions ouvertes

- **Deux `--watch` simultanés sur le même portail** : le risque de double-traitement par absence de lockfile est déduit du code (chaque process a son propre `Set vus` en mémoire), mais je ne l'ai pas fait échouer en pratique — un test de double-lancement réel aurait pu être bruité par les nombreux process Windows déjà en cours sur ce poste (plusieurs `node.exe` sans rapport tournaient pendant l'audit) et risquait de laisser un troisième process orphelin. À trancher par un test isolé, pas par ce corpus.
- **Écriture concurrente à grande échelle** : le test à 8 écrivains simultanés n'a montré aucune corruption, mais `appendFileSync` sur Windows n'a pas de garantie documentée d'atomicité au-delà d'un certain volume ou d'une certaine taille de ligne. Le corpus ne permet pas de fixer un seuil de rupture.
- **G8 (le harnais aide-t-il ?)** : `GATES.md` la déclare non franchie. Je ne peux pas la trancher non plus — elle demande une comparaison avec un appel direct à un modèle sur le même lot de contrats, hors périmètre de cet audit (pas d'accès à un modèle pour comparer, et ce n'est pas la question posée ici).
- **Le compteur de cycles de dormance (défaut #6)** : combien de cycles sans déclencheur transformeraient, selon la doctrine du propriétaire, une dormance en mort ? Le PRD pose la distinction mais ne donne aucun seuil chiffré. Sans seuil déclaré, même un compteur ajouté au code resterait arbitraire.

## Ce qui manque

- **Un superviseur de processus** pour le mode `--watch` : au minimum un heartbeat journalisé à intervalle régulier (pour qu'un silence prolongé soit visible dans `--journal` et distinguable d'une dormance), idéalement une relance automatique (service Windows, `pm2`, ou tâche planifiée qui vérifie la présence du process et le redémarre).
- **Une file de reprise** pour les fichiers déjà présents dans le portail au démarrage sans verdict correspondant dans le journal — au lieu de les classer aveuglément comme « déjà vus », le kernel devrait comparer le contenu du dossier au journal et rejouer ce qui n'a pas de `legal.gate` terminal.
- **Un détecteur de chaîne causale incomplète** : une commande qui liste les `contract.master_agreement.received` sans `legal.gate` en aval (contrats orphelins, défaut #3).
- **Un compteur de cycles de dormance par domaine**, exposé par `--autotest` ou une commande dédiée, avec le seuil au-delà duquel le PRD considère un domaine mort plutôt que dormant — seuil aujourd'hui non déclaré nulle part dans le corpus.
- **Une vraie architecture « fichier Markdown = nouvel agent »** si la promesse du §3.3 du PRD doit tenir : un interpréteur générique qui charge `accepts`/`tools`/`returns` du frontmatter et n'exécute que la logique déclarée, au lieu de fonctions JS dédiées par domaine. Tel quel, le 2ᵉ des huit domaines coûtera autant de code que le premier.
- **Un connecteur sortant**, déjà noté comme manquant dans `GATES.md:70` — le verdict est journalisé, jamais notifié à personne.
